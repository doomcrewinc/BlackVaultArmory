# Field encryption at rest — design (spec 3a of the auth epic)

Status: approved in conversation 2026-09-30, awaiting written-spec review.
Builds on: spec 1 (public URL, 1a4fb8a), spec 2a (accounts, 9f57074), spec 2b (audit log, 663523c).
Next: spec 3b (encrypted uploaded files) reuses this spec's key.

## Goal

Serial numbers and NFA paperwork are stored encrypted with a key held by the server. Signed-in users see
them exactly as today. Anyone holding only the disk, the data volume, a database dump or a backup file
cannot read them.

## Threat model

In scope, all chosen by the user:

1. A stolen or copied disk or Docker data volume.
2. A leaked backup file.
3. A leaked database dump, or a direct read of the SQLite file or Postgres.
4. Compliance: these values are never stored in plain text.

Accepted risk: an attacker who controls the running server can read everything. The key sits on that
server, so this is encryption at rest, not zero-knowledge.

Out of scope:
- Data in transit. The user's TLS reverse proxy covers it. Direct plain-HTTP LAN access is already
  flagged in the admin UI.
- Uploaded files (spec 3b).
- Tamper evidence.
- Case-insensitive serial matching.

Two consequences follow from this model:
- The key never lives on the data volume.
- Backups are sealed independently of the key.

## 1. Key, format and fingerprint

### Master key

- 32 random bytes, written as 64 lowercase hex characters.
- Loaded from, in order:
  1. The file at `BLACKVAULT_ENCRYPTION_KEY_FILE`, default `/run/secrets/blackvault_encryption_key`.
  2. The env var `BLACKVAULT_ENCRYPTION_KEY`.
- Surrounding whitespace in the file is ignored. Any other content fails validation.
- If both sources are present and differ, the app refuses to start.

### Subkeys

Two subkeys are derived with HKDF-SHA256, empty salt, from the master key:

| Subkey | HKDF info string | Used for |
|---|---|---|
| Encryption | `blackvault/field-encryption/v1` | AES-256-GCM |
| Index | `blackvault/serial-index/v1` | HMAC-SHA256 fingerprint |

### Key id

The key id is the first 8 hex characters of SHA-256(master key). It is logged and stored; the key
itself never is.

### Ciphertext format

`bv2:<keyId>:<iv b64url>:<ciphertext b64url>:<tag b64url>`

- Algorithm: AES-256-GCM with a random 12-byte IV per value.
- AAD is the UTF-8 string `<Model>.<field>`, for example `Firearm.serialNumber`. Moving a value into
  another column makes it fail to decrypt.

### Non-string fields

`nfaApprovalDate` (DateTime) and `nfaTaxPaid` (Float) become String columns. This is a type-changing
migration on both providers.

- Before encryption the extension serializes them as follows:
  - a date as an ISO string, under the existing date-only rule (UTC midnight);
  - a number as a JSON number.
- On read it converts them back, so application code still sees `Date` and `number`.

### Serial fingerprint

- A new nullable column `serialNumberHash` on Firearm, Accessory and Gear.
- Value: HMAC-SHA256(index subkey, the serial exactly as stored today, with no normalization), as hex.
- `Firearm.serialNumber @unique` moves to `Firearm.serialNumberHash @unique`.
- Accessory and Gear keep allowing duplicate serials. Their fingerprint gets an index for lookup.

### Key check

- `AppSettings.encryptionKeyCheck` holds the ciphertext of the fixed string `blackvault-key-check`
  (AAD `AppSettings.encryptionKeyCheck`).
- It is created on the first run that has a key.
- On every start, a failure to decrypt it means refuse to start. The log names the expected key id and
  the provided key id.

### Legacy values

Pre-V1 values in the `enc:` format (`src/lib/crypto.ts`) are recognized only by the upgrade migration
(§2). After this spec ships, `src/lib/crypto.ts` is removed.

## 2. Extension and startup

### Client order

`base client → encryption extension → audit extension`, exported from `src/lib/prisma.ts`.

The audit layer sees plaintext args and decrypted rows, and redacts them. The first plan task is a
real-DB proof, run on SQLite (`connection_limit=1`) and on Postgres, that these all pass through
encryption:
- audit before-row reads;
- audit writes, including nested creates;
- the audit transaction re-dispatch.

### Writes

The extension handles `create`, `createMany`, `update`, `updateMany`, `upsert` and nested writes on
every model with an encrypted field. For each write it:
- encrypts the listed fields;
- sets `serialNumberHash` whenever `serialNumber` is written.

`null` stays `null`, with a `null` hash.

### Reads

Every result is decrypted in place, including nested `include`/`select` results. A value that fails to decrypt throws `EncryptedFieldDecryptError`, carrying the model, id and
field. Ciphertext is never returned to callers.

### Filters

- `where` equality on `serialNumber` (`{ serialNumber: "X" }` or `{ serialNumber: { equals: "X" } }`)
  is rewritten to `serialNumberHash`.
- Any other operator on an encrypted field throws `EncryptedFieldQueryError`. That covers
  `contains`, `startsWith`, `endsWith`, `in`, `not`, `gt`/`lt`, `mode`, and use in `orderBy`,
  `distinct`, `groupBy` or `cursor`.
- Equality on the other encrypted fields also throws, because they have no fingerprint.

### Registry and guard tests

- One registry, `src/lib/encryption/fields.ts`, lists `{ model, field, kind: "string" | "date" | "number" }`.
- A guard test fails if any `$queryRaw` or `$executeRaw` in `src/` or `scripts/` mentions an encrypted
  column.
- A second guard test fails if an encrypted field's schema type is not String.

### Startup sequence (`src/instrumentation.ts`, Node only)

1. **Load the key (§1).** On failure, log one line naming each source that was checked, then exit
   non-zero.
2. **Key check.** Create it if absent and the database has no encrypted values. If it is absent but
   `bv2:` values exist, refuse to start (the key check was lost). A mismatch also refuses to start.
3. **Date migration.** The existing `runStartupDateMigration` runs next. It must reach
   `nfaApprovalDate` through the encryption extension, or skip values already in `bv2:` form. A test
   pins this.
4. **Encryption migration**, in one transaction:
   - Select every row where a listed field is non-null and does not start with `bv2:`.
   - Decrypt `enc:` values with `VAULT_ENCRYPTION_KEY`. If an `enc:` value exists and that key is
     absent or wrong, roll back and refuse to start, naming the row and field.
   - Encrypt each value and fill `serialNumberHash`.
   - Write one `ENCRYPTION_ENABLED` audit event: actor `system`, `changes: { counts: {Model: n} }`,
     `keyId`. No event is written when nothing changed.

   The migration is idempotent. Any failure rolls back and refuses to start, logging the model, id
   and field.

### Refuse to start

This follows the existing `BLACKVAULT_PUBLIC_URL` check at the top of `src/instrumentation.ts`. It
differs from the date migration, which logs and continues.

## 3. Backups, rotation, scripts

### Sealed backup format

```json
{
  "format": "blackvault-sealed-backup",
  "version": 1,
  "kdf": { "name": "scrypt", "N": 65536, "r": 8, "p": 1, "salt": "<b64url 16 bytes>" },
  "cipher": "aes-256-gcm",
  "iv": "<b64url 12 bytes>",
  "tag": "<b64url>",
  "data": "<b64url ciphertext>"
}
```

- The AAD is the canonical JSON of every field except `data` and `tag`.
- The plaintext is the existing backup JSON. Encrypted fields appear decrypted, because the backup
  route reads through the extension.

### Backup UI (`/settings`, admin only)

- Passphrase and confirmation fields; the passphrase must be at least 12 characters.
- Over direct plain-HTTP access, a warning is shown before sending.
- The download is `blackvault-backup-<date>.sealed.json`.
- `BACKUP_CREATED` records `sealed: true`.

### Restore

- A sealed envelope asks for the passphrase. A wrong passphrase or a damaged file returns
  "Wrong passphrase or damaged file" (HTTP 400) and writes nothing.
- A plain JSON backup restores after a warning that the file is not encrypted.
- Restored values are written through the extension, so they are encrypted with the current key.
- `RESTORE` records `sealed: true|false`.

### Shared crypto core

`src/lib/encryption/core.mjs` is plain ESM, with `core.d.ts` beside it. It holds:
- key parsing and loading;
- HKDF subkeys;
- field encrypt/decrypt;
- the fingerprint;
- seal/open for backups;
- the key id.

The app (`allowJs` is on) and the CLI scripts import this same file. There is no second copy of any
crypto logic.

### Rotation

Host wrappers `rotate-key.sh` and `rotate-key.bat` run these steps:

1. Stop the app.
2. Snapshot the database (same as the update scripts).
3. Generate the new key into `secrets/blackvault_encryption_key.new`.
4. Run `docker compose run --rm blackvault node scripts/rotate-encryption-key.mjs`, which in one
   transaction:
   - re-encrypts every listed field;
   - recomputes every `serialNumberHash`;
   - replaces `encryptionKeyCheck`;
   - writes `KEY_ROTATED` (actor `system (key rotation)`, `changes: { from: oldKeyId, to: newKeyId, counts }`).
5. On success, move the old key to `…key.old` and the new key into place.
6. Start the app.

On any failure the database transaction rolls back, the key files are left as they were, and the
reason is printed. The script refuses to run if the stored key check does not match the current key.

### Installers

`install.sh` and `install.bat` create `secrets/blackvault_encryption_key`:
- with mode 600 on Linux/macOS, or an ACL restricted to the current user on Windows;
- with a boxed message: "BACK THIS FILE UP. Without it your serial numbers and NFA records cannot be
  recovered."

### Update scripts

`update.sh` and `update.bat` do the following:
- Create the key if it is missing, with the same message.
- Snapshot the database into `backups/` next to the compose file, before the new image starts:
  - SQLite: a copy of the database file taken with the app stopped;
  - Postgres: `pg_dump` via the db container.
- Say that the snapshot is plaintext and can be deleted once the upgrade is confirmed.
- Stop the update if the snapshot fails.

### Compose

- A `secrets: blackvault_encryption_key: file: ./secrets/blackvault_encryption_key` entry, mounted into
  the app service.
- `BLACKVAULT_ENCRYPTION_KEY` is passed through, empty by default.
- `VAULT_ENCRYPTION_KEY` stays passed through for the legacy `enc:` upgrade path.
- The rule that env keys use the `BLACKVAULT_` prefix applies to every new key.

## 4. Errors, testing, acceptance

### Errors

- Every startup failure produces one log line with a fix hint, then a non-zero exit.
- Runtime decrypt failures surface through the normal error boundary. Ciphertext is never rendered.
- Unsupported queries throw, so tests catch them.

### Tests

- **Unit:**
  - round-trip;
  - a tampered ciphertext fails;
  - an AAD swap fails;
  - a wrong key fails;
  - fingerprint stability, and the fingerprint differs across keys;
  - sealed-backup round-trip, wrong passphrase, and a tampered envelope header.
- **Real-DB, SQLite and Postgres:**
  - every write kind, nested writes, reads with `include`;
  - serial equality lookups, and the duplicate firearm serial rejected;
  - the audit layer sees plaintext and redacts it;
  - the migration is idempotent and rolls back fully on failure;
  - the `enc:` legacy path;
  - rotation end to end.
- **Guards:**
  - the registry and schema types agree;
  - no raw SQL touches encrypted columns;
  - the date migration and the encrypted `nfaApprovalDate` coexist.
- **Injection proofs:**
  - remove encryption from one write path, and a test must fail;
  - remove the AAD, and the swap test must fail.

### Acceptance criteria

1. **Fresh install.** Reading the database directly (`sqlite3`, `psql`) shows `bv2:` ciphertext for
   every listed field that has a value. The app shows plaintext.
2. **Upgrade from `develop`**, on SQLite and on Postgres, with data present:
   - a snapshot is taken;
   - every listed field is encrypted;
   - a canonical app-level inventory hash is unchanged;
   - exactly one `ENCRYPTION_ENABLED` event is written;
   - a second start changes nothing.
3. **Key problems.** A missing key, a conflicting file and env var, a wrong key, or a lost key check
   each refuse to start with the documented message. No row changes.
4. **Duplicate serial.** Creating a firearm with an existing serial fails exactly as it does today.
5. **Sealed backup:**
   - the file contains no plaintext serial, name or note;
   - it restores onto a fresh install with a different key;
   - a wrong passphrase changes nothing;
   - an old plain backup restores after the warning.
6. **Rotation:**
   - every value carries the new key id;
   - the old key no longer starts the app;
   - one `KEY_ROTATED` event is written;
   - a failed rotation leaves the database and the keys unchanged.
7. **Nothing else changes.** Search, exports, PDFs and item pages behave as before. The audit log shows
   NFA fields and serials as redacted.
8. **CI.** The Windows `.bat` changes pass the Windows installer job, and CI is green on both
   time-zone legs.

## Known limitations

- Anyone controlling the running server, or holding both the key file and the data, can read
  everything.
- Encrypted fields cannot be searched, sorted or filtered, apart from exact serial match.
- Exports (CSV, PDF, full armory) contain plaintext by design. The export page says so.
- The update script's pre-upgrade snapshot is plaintext until the user deletes it.
- Losing the key file makes the encrypted fields unrecoverable. Sealed backups can still be restored
  with their passphrase.
