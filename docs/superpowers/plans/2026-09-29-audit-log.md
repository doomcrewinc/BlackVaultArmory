# Audit Log Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Record every inventory/settings write and every security event as a permanent, admin-only, append-only `AuditEvent` naming the account that did it.

**Architecture:** A Prisma client extension (Prisma 5.22 `$extends` query component) captures create/update/delete on audited models, reads "before" rows, and writes the audit row in the same transaction; the actor comes from `getCurrentUser()` via Next's request context. Security events are explicit `recordEvent` calls. A registry plus a DMMF guard test forces every model into "audited" or "excluded". Admin UI at `/admin/audit` with filters, item History sections and CSV export.

**Tech Stack:** Next.js 16.1.6 (App Router, `proxy.ts`), Prisma 5.22 (SQLite + PostgreSQL, client extensions), React 19, vitest (+ jsdom per file), Tailwind `vault-*` tokens.

**Spec:** `docs/superpowers/specs/2026-09-29-audit-log-design.md`

## Global Constraints

- Actions (exact strings): `CREATE` `UPDATE` `DELETE` `LOGIN` `LOGIN_FAILED` `LOGOUT` `INVITE_CREATED` `INVITE_REDEEMED` `ROLE_CHANGED` `USER_DISABLED` `USER_ENABLED` `RESET_LINK_ISSUED` `PASSWORD_CHANGED` `DIRECT_ACCESS_CHANGED` `BACKUP_CREATED` `RESTORE`.
- `actorName` snapshot format: `"<displayName> (@<username>)"`, or exactly `"system"` / `"anonymous"`.
- Redacted value (exact): `"[redacted]"`. Redacted fields: `serialNumber`, `passwordHash`, `tokenHash`, `googleCseApiKey`, and any field whose name matches `/secret|token|password|apikey/i`.
- Audited models: Firearm, Accessory, AmmoStock, AmmoTransaction, Gear, Supply, Kit, KitItem, Build, BuildSlot, Document, MaintenanceLog, BatteryChangeLog, RangeSession, RangeSessionAmmoLink, SessionDrill, RoundCountLog, AppSettings. Excluded: Session, AuthToken, User, ImageCache, DateNormalizationAudit, AuditEvent.
- Entries are kept forever; no code path updates or deletes an `AuditEvent`.
- `AuditEvent` is in `BACKUP_EXCLUDED_MODELS`; the SQLite→PostgreSQL migrator copies it, after `User`.
- JSON stored as `String` text; enum-like fields are `String` + a TS const/union (repo convention).
- `actorIp`: last `X-Forwarded-For` value only when `trustsForwardedHeaders()`; otherwise null.
- Failed-login username: trimmed, capped at 64 characters, no actor.
- CSV: RFC 4180 escaping; a cell starting with `=`, `+`, `-`, `@`, tab or CR is prefixed with `'`.
- Admin only: `/admin/audit`, `/api/admin/audit*`, item History sections. API 403 `{ "error": "Admins only" }` via `requireAdmin()`.
- Schema: edit only `prisma/schema.base.prisma`; `npm run gen:schemas`; `npm run db:generate`; SQLite incremental + PostgreSQL own timestamped migration (`0_init` frozen); drift check both.
- Never `git add -A` (install.bat/update.bat CRLF-index quirk). Branch `feat/audit-log` off `develop`. PRs `gh pr create --repo doomcrewinc/BlackVaultArmory --base develop`; CI runs only on PRs → open a DRAFT PR when CI is first needed; never merge.
- Prove every guard by injection (executed, FAIL output shown).
- This plan's execution is permission to run vitest, `npm test`, typecheck, lint, build, `npm start`, and local Docker of this repo's image and scratch containers. Never touch the `dashboard` host or the user's `prisma/prisma/dev.db` (use scratch copies).

## Review Focus

1. **A write inside an existing interactive `$transaction` on SQLite (`connection_limit=1`)** — must not deadlock and must roll back together with its audit row. Pinned in Task 2 and Task 4.
2. **Deleting a firearm with many children** — one DELETE entry with `_children` counts, not dozens of entries and not zero. Pinned in Task 4.
3. **A route that updates a row with the same values it already has** (common in form saves) — no audit entry. Pinned in Task 4.
4. **An item name containing `=HYPERLINK(...)` or a comma/quote/newline** — CSV opens safely and parses to the original text. Pinned in Task 6.
5. **Startup jobs writing inventory (date migration) before any request exists** — recorded as `system`, never throwing because `cookies()` is unavailable. Pinned in Task 4.

```ts
import { trustsForwardedHeaders } from "./request-gate";

/**
 * The client's address as the trusted reverse proxy saw it: the LAST
 * X-Forwarded-For value (the one our proxy appended; earlier values are
 * client-controlled — same rule as the login throttle, ruling A8). Without
 * configured trusted proxies nothing in the headers can be trusted, so null.
 */
export function getClientIp(request: Request, env: NodeJS.ProcessEnv = process.env): string | null {
  if (!trustsForwardedHeaders(env)) return null;
  const values = (request.headers.get("x-forwarded-for") ?? "")
    .split(",")
    .map((v) => v.trim())
    .filter(Boolean);
  return values.at(-1) ?? null;
}
```

### Task 2: Spike — request context and transaction joining (GATE)

**Files:**
- Create: `docs/superpowers/specs/2026-09-29-audit-log-spike.md` (findings, committed)
- Scratch only (deleted before commit): a throwaway extension + route under `src/app/api/__spike__/` and a real-SQLite test

**Goal:** Decide, with evidence, how the extension (a) resolves the actor and (b) writes the audit row atomically. Prisma 5.22 does not expose the surrounding interactive-transaction client to a query extension hook, and this app runs SQLite with `connection_limit=1`, where opening a second transaction while one is open **deadlocks** (it waits for the only connection).

Probe each on real SQLite (temp DB migrated with `prisma migrate deploy --schema prisma/sqlite/schema.prisma`) through a real route handler under `next start` or a vitest that invokes the route handler with Next's request context (whichever the repo's existing route tests make possible — prefer the real server for (1)):

1. `cookies()` / `headers()` from `next/headers` are readable inside a `$extends({ query: { $allModels: { $allOperations } } })` hook when the write happens: (a) directly in a route handler; (b) inside a `prisma.$transaction(async (tx) => …)` callback; (c) in `instrumentation.register()` (expect: throws → must map to `system`).
2. **Transaction joining candidates**, each tested for: audit row committed with the change; both rolled back when the caller's transaction throws; no deadlock with `connection_limit=1`; works on PostgreSQL too (scratch `postgres:17-alpine` container, removed after):
   - **(A) AsyncLocalStorage transaction context:** wrap `prisma.$transaction` (the app's exported client) so interactive callbacks run inside an ALS store holding `tx`; the hook writes the audit row with `store.tx` when present, and otherwise wraps the single operation as `base.$transaction(async (tx) => { result = await <op via tx>; await tx.auditEvent.create(...) })`.
   - **(B) Batched write:** for single operations outside a transaction, `base.$transaction([op, auditCreate])` (array form) — only works when "before" data is already read and the op is expressible without `query(args)`.
   - Any Prisma-documented alternative found in the 5.22 docs (check context7 for "client extensions transactions query component").
3. What `query(args)` does when called from within an interactive transaction (does it run on the tx connection?).

- [ ] **Step 1:** Build the probes in scratch files. Run each. Record raw output.
- [ ] **Step 2:** Write the findings doc: for each probe, method, output, verdict; then **Decision**: the chosen mechanism for actor resolution and for atomic audit writes, with the exact API shape Task 4 will implement (function names, where the ALS lives, how `$transaction` is wrapped).
- [ ] **Step 3: GATE.** If no candidate achieves atomic same-transaction writes on BOTH providers without deadlock, report **BLOCKED** with the findings — the controller must return to the user before Task 4. Otherwise report DONE.
